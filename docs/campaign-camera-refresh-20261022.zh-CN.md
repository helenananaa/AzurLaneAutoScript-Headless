## 地图失败的根因与修复

- 无待执行输入计划时，整图签名冻结拒绝了入图正常刷怪。删除此只读观察限制，
  有待执行输入时仍验证该计划依赖的地图身份。
- 原截图边界内反复读取 live 地图以证明 generation 增长，与 immutable frame
  语义冲突。相机只读投影改用当前冻结帧；输入准备仍使用原有稳定状态证明。
- 舰队移动、目标进入 fighting 状态、补弹拾取会改变真实地图。将这些变化接入
  原 ALAS 的移动/战斗流程；补弹只允许选中舰队获得有界弹药，保持战斗计数和
  无关地图状态，未增加另一个路径规划器。
- 地图切换到准备/战斗时，相机瞬时缺少锚点。转换为原 `MapDetectionError`，由
  原 `Camera.update()` 刷新及超时；已提交战斗的过渡回到原 NativeGoto 循环。
- 自动开始后 Start 控件消失，按现有目标缺失分类处理，并要求新帧证明战斗或
  加载；不伪造点击收据。ChapterPreCombat 信息弹窗由原专用处理器接管。
- 手动 Boss 结算曾走适配层快捷等待，跳过原经验/统计/奖励处理，导致卡住。
  删除整个快捷分支，恢复原 Combat.status 流程及原关卡结束判定。
- 原 UI 恢复优先处理遗留结果页；只恢复到已证明的普通关卡页，不把中断任务
  宣称为完成。`GET_MISSION` 使用精确委托通知正负观察，避免奖励页误判。
- Redroid 的输入前慢前台查询使信息弹窗、准备页 Back、紧急委托及舰队编号的 Button/UI
  相隔过多 generation。统一先完成端点配对再检查前台；信息弹窗点击使用已证明的
  同一份状态，只重读未提交的观察，不重放输入。两次失败出击共消耗 20 石油，
  两次恢复与失败收据分开保留，最终完整运行发生在这些修复之后。
  另一次六场普通战斗后的切换舰队失败消耗 454 石油，保留为失败诊断，未计为完成。
  免费生产资源读取也修正同样的端点配对顺序。
- AVD 的一次运行在 Boss 结束后暴露 GET_MISSION 点击仍被通用战斗别名截走。
  点击分派改由精确紧急委托端口接管；被遮挡或尚不可操作的提示不触发原 handler。
  原 InfoHandler 单独关闭实际提示的验证通过，后续一次导航失败保留为失败恢复，
  再次原 UI 导航回到健康主页。该失败 Main 消耗 534 石油，没有计为完整成功。

## 已删除的过度防御

除整图冻结和结算快捷分支外，还删除船坞 Back 后重复强制主页的 12 秒等待、
适配准备页重复 60 秒计时、非地图页面的全局历史白名单，以及只读相机重定位
固定 5×4 范围限制。Viewport 几何查询使用当前唯一控件的位置/边界，不再套用
旧网格点击的 5 像素漂移限制；实际网格点击与手势的许可及后置条件仍保留。
非 Mail 上下文的完整帧若没有邮件返回控件，返回普通缺席，不再阻断无关任务。

没有删除实际输入的包名、前台/PID、新鲜同代状态、唯一可操作目标、遮挡及
后置条件检查。缺失、模糊、截断或不受支持的输入仍拒绝；没有像素/OCR/坐标回退。

## 退役与恢复的独立证据

满仓布局新增 `select_panel_adapt` 包装，解析兼容该层，收据保留真实路径。
observer 补齐精确 quick_select raycast 导出；配对读取避免夹入慢前台查询。
满仓弹窗只在输入前重绑整个 Button/UI 观察，不重试点击。
退役后原 ALAS 重新进入关卡时，仅清理未出击的旧准备上下文，不重置任务额度。

原退役流程单独证明退役 150 艘并保留装备。早期 Redroid 完整 Main 也曾通过，
但属于旧代码，摘要单独列出。这些记录不证明“中途满仓→退役→继续→完成”的
单进程不中断链路。一次强化诊断未观察到结果，未重放提交，强化仍未资格化。
